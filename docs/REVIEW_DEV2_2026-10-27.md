Scope: `git log 45e5edc..main` (main 4963ec1, 51 commits, 150 files, +5217/-532): the security wrapper and gates, Electron
45.0.0-beta.3 → 45.1.0, the engine (arena `sharing`, TIGHT window tables, Core ML defaults and two-size set, CLI linear
default), the app (EXR frame folders, stills, GPU names, keep-awake, Core ML setup download, drawer focus), the farm
submitters, the 22 gates and pre-commit hook, release.sh / upload_model_set.sh / publish_wiki.mjs, and the dev.2

What I ran: `tsc --noEmit` on tsconfig.app / electron / node (all clean, memory-capped); read-only `gh release view` /
`gh run list`; one read-only `node tools/check_wiki.mjs --published` against a shallow wiki clone in scratch (the

## Verdict

**Ship dev.2 after the release steps, S1 (CHANGELOG, ~15 min), and a decision on S2.** No MUST. Grade **B+**
(security and app work A-; held back by gates that can pass without guarding anything and one unmeasured default path).

The security work is right: one wrapper at registration for every channel, a gate for it, deny-all permissions, strict
CSP, navigation and window-open locked. The CLI / app / farm agreement on scene-linear frame folders is consistent end to
end and well tested. What's weak: the 8 GB "window" headline rests on measurements taken under a memory limit while the
app's default (Auto) runs without one; the context-overhead "counted as 0" leaks into later jobs; and two gates (docs
touch, pre-commit) are mostly inert in the way work actually lands here.

**Release steps (blocking, not defects):** package.json and the lock are still 1.0.0-dev.1; the CHANGELOG header is
`## 1.0.0-dev.2 (draft, unreleased)` (release.sh:42 refuses it, correctly). Bump with
`npx -y npm@10.9.2 version 1.0.0-dev.2 --no-git-tag-version` and rename the header. Note: run release.sh *before* the bump
and it does not refuse: v resolves to 1.0.0-dev.1, `state=false`, and it silently "redoes the feeds" for dev.1 (N13).

## SHOULD

### S1. CHANGELOG dev.2 leaves out two user-visible changes and states one unmeasured result as fact
- **Where:** CHANGELOG.md:3-110.
- **Missing:** (a) keep-awake (55e0346, index.ts:240,254): the computer no longer sleeps while the queue runs, on every
  system. A user will notice that (a laptop that used to sleep now doesn't). (b) Every IPC channel now checks its sender
  and the page gets no permissions (d1eb027). Line 54's "security policy is stricter" covers the CSP only.
- **Inaccurate:** line 77-78, "1280×1080 clips get 24/12 (was 8/4)": that is 24/12 *low-VRAM* (vram.rs test
  `an_8_gb_card_gets_the_window_it_ran`); and "6 GB cards get 8/4 at 1920×1080 (was 2/1)" is what the selector picks at
  ~5.5 GiB, but ENGINE_RUST.md:245-248 says budgets under 7.0 GiB were never measured. At 5.5 GiB the 8/4 low-VRAM
  estimate is 4.71 against a cap of 4.727 GiB, 0.02 GiB from the edge, so "get" overstates it.
- **Fix:** add the two lines; say "24/12 in low-VRAM mode"; "6 GB cards: 8/4 at 1920×1080 (was 2/1), not yet measured
  on a 6 GB card".

### S2. 8 GB cards on Auto (the app's default) get a window measured only under a memory limit
- **Where:** vram.rs:133-144 (a window fits when its TIGHT peak fits); pipeline/mod.rs:645-648 (`vram_cap` is set only
  when the job has a `vram_budget_gb`; Auto has none, so no arena is capped); ENGINE_RUST.md:229-248 (all 68 runs on
  the RTX 2070 SUPER had a 7.0 / 7.4 GiB `vram_budget_gb`; "Not measured: the app's Auto").
- **What goes wrong:** on Auto, an 8 GB card now picks 1280×1080 24/12 low-VRAM (dev.1: 8/4) and 1920×1080 8/4 normal
  (dev.1: low-VRAM) from peaks measured with capped arenas, then runs with uncapped ones. If the peaks follow the
  16 GB table instead (8.04 GiB at 1280×1080 24/12 low), stage 1 runs out of memory. The automatic window's
  out-of-memory retry halves and restarts (it re-runs RVM and the foundations first), so the likely failure is a
  slower job than dev.1, not a lost one. But this is the main path for the README's floor hardware, and the CHANGELOG
  sells it as the improvement.
- **Fix, one of:** (a) measure it (run below) before release; or (b) for dev.2, take the TIGHT reading only when the job
  has a limit: pass `budget_gb` to `estimate_peak_vram_gb` from `select_vram_profile` only when `job.vram_budget_gb`
  is Some, else None (roomy table, dev.1's windows). That's one line at the call site, and the tests keep passing for
  the limited case. Then say so in the CHANGELOG.
- **Run that proves it (for Marcy to approve):** on an 8 GB card with no limit (the 2070 SUPER is the Mint box: only on
  Marcy's explicit OK, memory says no GPU work there), `tools/engine_bench.mjs` with *no* `vram_budget_gb`, a
  1280×1080 clip of ≥ 48 frames and a 1920×1080 one. Pass: the `memory` reply shows 24/12 low / 8/4 normal,
  no `oom` / retry line in the log, nvidia-smi peak ≤ free memory at start. A 5080 with a memory hog leaving 7.4 GiB free
  is a weaker substitute (other architecture, which ENGINE_RUST.md names as a possible cause).

### S3. "Counted as 0" context overhead outlives its job and removes the context reserve from later low-VRAM arenas
- **Where:** pipeline/mod.rs:395-406 sets `gpu_overhead = Some(0)` when C-RADIO (loaded first: runtime.rs:18 PIECES)
  takes less on the card than its file, which f216af9 says is every normal-mode job. It is never reset (only initialised
  at :270) and is used at :552 instead of the 0.5 GiB default.
- **What goes wrong:** with a graphics-memory limit set (App settings, `--max-vram`, OpenCue/Deadline MaxVram), a
  queue that runs a normal-mode job and then a low-VRAM one in the same engine process (an HD clip then a 4K clip) sizes
  the second job's arenas as if the CUDA context (~0.33 GiB, jobs.rs:538) took nothing. In normal mode C-RADIO's
  oversized file makes up for it, which is why the comment says "tighter", but in low-VRAM `sharing("stage1") = [stage2]`
  (mod.rs:1243) has no C-RADIO term. Stage 1's arena is then ~0.33 GiB larger than designed, and the 0.5 GiB reserve
  was measured needed at 0.17-0.22 (mod.rs:538-541): about 0.05 GiB over the user's limit at worst. A small overshoot,
  but it breaks the stated rule (the limit is what leaves room for Sonata or Nuke).
- **Fix:** when `own < w`, leave `gpu_overhead` None so the 0.5 GiB default stays, and let the next load measure it
  (`self.gpu_overhead = (own >= w).then(|| own - w)`). Then the log line "counted as 0" becomes "0.5 GiB assumed".
- **Run that proves it:** one engine process, `CK_ENGINE_VRAM_BUDGET_GB=4`, a queue of a 1920×1080 normal-mode job then
  a 4K low-VRAM 1/1 job. Compare the second job's `loaded stage1 … arena limit X GiB` with the same 4K job in a fresh
  process: today X is ~0.5 GiB larger. Also log nvidia-smi's peak for the process against 4.0 GiB.

### S4. The Mac setup never updates a Core ML set it has already installed
- **Where:** install.ts:317: the set counts as installed once *any* coreml.json is in the model set's folder. 7dd19d7
  pinned a 395-byte coreml.json (1280×1080 only); f5663fd replaced it with the 851-byte two-size one and clobbered it on
  GitHub.
- **What goes wrong:** a Mac that ran setup between those commits (the Mac mini) keeps the old coreml.json, never
  downloads the 1920×1080 files, and a 1920×1080 clip fails with "the Core ML set has no models for 1920x1152 frames".
  The next set change (4K, row 60) repeats this for every Mac user. Not a dev.2 blocker (no Mac build), but it must be
  fixed before the first one.
- **Fix:** treat the set as installed only when coreml.json has the pinned size and SHA-256 (851 bytes, cheap to hash);
  otherwise download the missing / changed files (`fetchOne` already keeps whole ones).

### S5. A rerun of release.sh after a failure publishes the draft at its old commit
- **Where:** release.sh:76: with `state=true` (a draft left by a failed run) the draft is neither re-targeted nor given
  new notes. The binaries uploaded at :77 are built from the current HEAD.
- **What goes wrong:** the documented recovery is "run it again" (RELEASING.md step 4). If anything was committed between
  the failed run and the rerun (the usual reaction to a failure), the tag `v1.0.0-dev.2` is created at the old commit,
  while the AppImage, the notes and the feeds come from the new one.
- **Fix:** for `state=true`, `gh release edit "v$v" --target "$(git rev-parse HEAD)" --notes-file release/notes.md`
  before the upload, or refuse when the draft's `targetCommitish` isn't HEAD.

### S6. The docs-touch gate can't see the commit that changes the CLI
- **Where:** check_docs_touch.mjs:49 reads `origin/main..HEAD`. The pre-commit hook runs before the commit exists;
  release.sh runs `npm run check` on a main that is normally already pushed; there is no CI on push (.github has
  windows.yml and macos.yml, both on demand only).
- **What goes wrong:** the case it was written for (0cdad0c changed args.rs with 2 of the 3 docs) still passes. Under
  "build → commit → push" the commit is pushed before any later gate run sees it, so the gate checks nothing.
- **Fix:** a `commit-msg` hook that checks `git diff --cached --name-only` and the message being committed, and in
  release.sh the range since the last release tag (`git describe --tags --abbrev=0`..HEAD).
- **Run that proves it:** in a scratch clone (`~/.cache/claude-scratch/…`), touch args.rs, commit without docs: the
  pre-commit passes; push to a local bare remote: `node tools/check_docs_touch.mjs` then reports nothing.

### S7. The pre-commit hook passes silently where agents commit
- **Where:** .hooks/pre-commit:5: no node_modules means `exit 0` with a note. None of the four worktrees in
  .claude/worktrees (amd, apple-step2, console, onnx5) has node_modules, so every agent commit there skips all 22 gates.
  core.hooksPath is per-clone config, set here but not set by any script (the laptop clone?).
- **Fix:** fail instead (`exit 1`, "run npm ci, or commit with --no-verify on purpose"), or run the gates with the main
  checkout's node_modules. Set core.hooksPath from an npm `prepare` script so every clone has the hook.

### S8. The CLI's Windows-only code has never run on Windows, and the CHANGELOG claims it works
- **Where:** signals.rs:52 (SetConsoleCtrlHandler), rundirs.rs:44/92, main.rs:17 (DLL search), appinstall.rs:175
  (PATH). `gh run list` shows windows.yml has never run. check_targets.sh only lints it.
- **What goes wrong:** CHANGELOG.md:24-25 says "a clean stop … also on Windows' console close, log-off and shut-down".
  Nothing has run that code.
- **Fix:** `gh workflow run windows.yml` once (GitHub CI, not the VM, so it fits the dev-build rule), or say "untested
  on Windows" in the line.

## What's solid

- **IPC:** every handler goes through `handle`/`listen` → `fromAppPageOnly` at registration (index.ts:862-863), the
  only `ipcMain` use in electron/. Sender = the window's webContents *and* its main frame (validate.ts:50-52). There is
  a gate and fixtures.
- **Window:** sandbox, contextIsolation and webSecurity on, nodeIntegration off (index.ts:1252-1256). Permission
  request and check deny all (:1276-1277), and the renderer uses no permission API (no navigator.clipboard,
  mediaDevices, Notification). will-navigate is prevented, window-open is deny-only, CSP has no unsafe-*, and the
  connect/frame/worker/object sources are 'none'.
- **Scene-linear end to end:** the CLI tri-state (flags conflict, args.rs:171; job-file type checked, run.rs:176;
  report says why), the app default by first frame, Copy as command writing both ways for EXR, OpenJD `null`,
  Flamenco `auto`, OpenCue/Deadline through flags. The tests cover the matrix (run.rs:723-743).
- **Low-VRAM `sharing`** (mod.rs:1237-1250) matches the actual unload/ensure/preload order in keying.rs
  (216/225, 297/300, 403/476, 557).
- **The TIGHT tables** are tested monotone at eight budgets, bounded by all 23 measured 8 GB points at seven budgets,
  out-of-memory points refused, and 12/16 GB windows unchanged (vram.rs tests).
- **Model releases:** all three carry the seven licence files, and the Core ML release's 13 assets match install.ts's
  pins byte for byte (size and GitHub digest). upload_model_set.sh is idempotent and verifies digests at the end.
- **The rest:** the published wiki equals docs/wiki/. The scripts never use a shell: publish_wiki.mjs and
  check_model_sets use execFileSync / fetch, the token goes only in the environment, and the signing key goes only to
  sign-feed. The GPU names change shows the program's name only, never arguments or home paths. The stills cache key
  changed, so no green stills are reused. TypeScript is clean in all three projects.
